# AI: engines, set-up and privacy

The app's AI is local-first. By default the model runs on this PC through Microsoft Foundry Local, on the NPU when there is one and otherwise on the CPU. Nothing is sent to an internet AI service unless you allow it. The offline features (log digests, rule-based reports, help search) work with AI switched off.

## What the AI does in the app

| Feature | Where | Can it change anything? |
|---|---|---|
| AI operator (chat + tools) | *Sidebar → AI operator*, "✦ Diagnose with AI", "✦ Ask AI" in a terminal | Only after you approve: each command, service or power action is shown first. Read-only lookups can run without asking (setting) |
| Log analysis | log viewers, "✦ Explain" on log lines | No |
| AI reports | *Reports* | No |
| Help & FAQ answers | *Help* (answers from the built-in articles) | No |
| "✦ Explain / review with AI" | files, documents, invoices, hosts, keys, cloud resources | No: content is sent only when you click |
| Screenshots | 📷 → "Analyse with AI" | No; needs a vision model (Ollama) |
| Claude Code launcher | *Settings → AI engine* | Runs Claude Code against a local Ollama model, in its own workspace folder |

Every AI feature can be switched off on its own (*Settings → AI engine → FEATURES*). The AI never types into a terminal: anything it wants to run is previewed and needs approval, and it's recorded in the audit log as actor `ai`.

## Engines

| Engine | Runs on | Typical use |
|---|---|---|
| **Foundry Local · NPU or CPU** (default) | this PC: NPU (Intel AI Boost, AMD XDNA, Snapdragon Hexagon) or CPU | laptops, Copilot+ PCs, low power |
| Ollama · GPU | this PC, a LAN machine, or a GPU server through an SSH tunnel to a saved host | a strong graphics card (8 GB VRAM or more), larger models |
| Ollama · CPU only | the CPU, forced | Ollama on a machine without a usable GPU |
| OpenAI-compatible server | LM Studio, llama.cpp, vLLM, LocalAI, Jan; or OpenAI / Azure OpenAI / a gateway | your own server, or a cloud service you allow |
| Anthropic Messages API | Claude (API key), or Ollama's Anthropic-compatible endpoint | Claude models, if you allow internet providers |
| Off | nothing | no model is ever called |

## The default: the best model for this hardware

The first time the app starts, it checks the hardware once and sets **Foundry Local** with:

| This PC | Model | RAM while answering |
|---|---|---|
| has an NPU | `phi-4-mini` (its NPU build) | low: the NPU does the work |
| no NPU, 16 GB RAM or more | `phi-4-mini` (3.8B; the GPU build with a capable graphics card, else the CPU build) | about 5 GB on the CPU |
| no NPU, 8–15 GB RAM | `qwen2.5-1.5b` | about 2 GB |
| no NPU, less than 8 GB | `qwen2.5-0.5b` (lightweight) | about 1 GB |

Since 0.1.8 these are **model names**, not builds. Foundry Local's catalogue on each PC decides which build runs (NPU / GPU / CPU, x64 or ARM64), so settings copied to another PC still work there.

- **Ollama is never chosen for you.** "Detect hardware" recommends the same Foundry model; with a strong GPU it also mentions Ollama as an option you can apply yourself.
- **Your choice wins.** The default is applied only to settings nobody has changed: a fresh install, the untouched old Ollama default of earlier versions, or a model an earlier default set. An engine or model you picked is never overwritten.
- **Upgrades:** when a new version changes the rule (0.1.6 did), it's applied once more under the same conditions.

## Setting up Foundry Local

**Hands-off (since 0.1.8).** With *Set up and repair automatically* ticked (the default), the app does it all a few seconds after it starts, and again whenever an AI request finds Foundry Local not answering. Every step shows in the status bar and under STATUS in Settings; installs, downloads and repairs go to the audit log.

| Step | What the app runs | Notes |
|---|---|---|
| Installed? | `foundry status -o json`; if missing: `winget install --id Microsoft.FoundryLocal -e --silent` | Microsoft's package; not in offline mode |
| Running? | `foundry server start --idle-timeout 0` (older versions: `foundry service start`) | keeps the service running |
| Answering? | `GET /v1/models` within 5 s; if not: `foundry server restart`, then stop + end the stuck `foundrylocald` + start | this is the "says Ready, load fails with exit 4" case |
| Which build? | `foundry model list --type chat --variants -o json` | the configured model's build for **this** PC; not offered → the recommended model |
| Downloaded? | `foundry model download <id>` | size shown first; not in offline mode; on battery an automatic run waits for mains when it's over 1 GB |
| Loaded? | `foundry model load <id>`; a failure → one repair + one retry; then `foundry model list --loaded` | |

**Buttons:**
- **Set up now:** the same steps, now.
- **Restart service**, **Stop service**, **Unload model**.
- **Show log:** `foundry server logs`.
- **Copy the commands:** for a terminal.
- **Test:** one chat request.
- **Errors** show Foundry Local's own message and code.

**Choosing the model:** *Show the models for this PC* lists what Foundry Local offers on this machine:
- grouped NPU / GPU / CPU;
- each with its size, whether it's downloaded, whether it can use tools (the operator needs this) and what it's good for;
- the recommendation for this hardware on top;
- *Use* switches to a model and loads it.

**Intel NPUs** (Core Ultra, "Intel AI Boost") need the Intel NPU driver for Windows from intel.com, or Foundry Local runs on the CPU. *Task Manager → Performance → NPU* shows the NPU working while the model answers.

### How the app talks to Foundry Local

- **Finding the service:** with FOUNDRY LOCAL ADDRESS empty, the app runs `foundry server status` and takes the local URL it prints (loopback preferred; port 0 ignored). If the CLI answers "Unknown command" (a version from before the `server` rename) it runs `foundry service status` instead. A typed address (for example `http://127.0.0.1:39839` after `foundry server start --port 39839 --idle-timeout 0`) skips the CLI.
- **Model names:** Foundry's OpenAI-compatible endpoint (`/v1/chat/completions`) needs a full model ID. A short alias such as `phi-4-mini` is resolved first, through `/foundry/list` and `/v1/models`: the NPU build, else GPU, else CPU, preferring one already downloaded. A full ID is sent exactly as typed, so a CPU model stays on the CPU.
- **CLI commands** run without a window and time out (status 15 s, start 2 min, model load 30 min).

### Troubleshooting

| Message | Fix |
|---|---|
| Foundry Local isn't installed | *Set up now* (installs it); if it then can't be found, restart the app |
| Foundry Local isn't running / doesn't answer | *Set up now* repairs it (restart, then a fresh start); *Show log* has Foundry's own messages |
| Unknown command: 'service' | an app version before 0.1.5: update the app |
| model … not found / not loaded | *Set up now*, or *Use* on a model from *Show the models for this PC* |
| Slow answers | a smaller model from the list, or mains power (Windows slows the CPU and NPU on battery) |
| Screenshot analysis refused | Foundry models here are text-only: use a vision model in Ollama for images |

## Privacy and network use

- **Local by default.** Foundry Local and Ollama on this PC or your LAN never send data out. Internet AI providers (OpenAI, Anthropic, any public address) are refused until you tick *Allow internet AI providers*, and they're marked ⚠ in the Privacy view.
- **Secrets are masked** before anything is sent (on by default): private keys, passwords, tokens, API keys, JWTs and credentials in URLs become `[REDACTED]`. If text can't be checked in time it is withheld, not sent.
- **"Data being sent" preview:** "✦ Explain / review" actions show exactly what goes to the model.
- **Offline mode** blocks every non-local AI address. The Foundry set-up then never installs Foundry Local or downloads a model; it says so, and only starts and loads what is already on the PC. Foundry Local's own catalogue check is outside the app's network control.
- **Battery:** *Pause automatic AI work on battery power* (on by default) stops background AI work when unplugged; your own requests still run.
- **Stored settings** (engine, models, addresses, API keys) are in the encrypted `settings.dcx`, like everything else.

## Running AI-suggested commands in a terminal (0.1.11)

### Choosing the target and running a command
- **Choosing a target:** the AI Engineer has a **TARGET TERMINAL** picker. Only the session chosen there can receive commands, and nothing switches it on its own. If that terminal disconnects, reconnects or closes, the choice has to be made again.
- **Running a command:** code blocks in an answer get **▶ Review & run in <session>**. The review shows:
  - the exact text;
  - the target (server, user, working directory, environment);
  - a risk rating with its reasons.
- **Confirmation by risk:**

| Risk | Examples | Confirmation |
|---|---|---|
| Read-only | `uptime`, `df -h`, `journalctl -u nginx`, `systemctl status`, `docker ps`, `Get-Service` | one click |
| Changes the system | `systemctl restart`, package installs, edits, redirections into files, any program not on the read-only list | warning; in PRODUCTION type the session name |
| Sensitive | passwords, users and sudo rights, SSH keys, certificates, `sudo -i` / `su`, piping a download into a shell, printing the environment | type RUN |
| Destructive | recursive deletes, `dd`/`mkfs` to disks, partitioning, reboot/shutdown, firewall flush, removing containers/VMs/volumes | type the session name |

### What happens when it runs
- **Visible:** the command is typed into that terminal, so you see it run.
- **Read back:** markers around it bring back the output, the exit status and the working directory.
- **Stop:** **■ Stop** sends Ctrl+C.
- **What the AI receives:** the output, masked and shortened, marked as untrusted terminal output.
- **Audit:** the target, the risk and the masked command are recorded, never the output.

### Which sessions work
SSH to Linux/Unix, WSL and local PowerShell. cmd, Windows or network-device SSH, serial and Telnet sessions can't report an exit status reliably, so they are listed as not usable.

### What you see typed in PowerShell (0.1.18)
- **The first command in a session** also defines a small helper, `__dcx`, which prints the markers the app reads back. This happens once per session.
- **After that each command shows as** `. __dcx <id> '<the command>'`, so you can read exactly what runs.
  - Variables it sets stay in your session, as if you had typed it.
  - A command over several lines, or with tabs or non-English characters, is sent Base64-encoded instead. The review still shows it in full.
- **If the helper is gone** (you removed it, or the session is now a nested shell), the app types it again by itself.
- **Risk labels:** `Get-WmiObject`, `Get-Member` and other reading cmdlets count as read-only. `powershell -Command "…"` and `pwsh -c "…"` are judged by the command inside them, but `-EncodedCommand`, `-ExecutionPolicy` and `-File` still count as changes. Calling a method on an object, such as `(Get-WmiObject …).Delete()`, counts as a change.

## Speed, agents and the AI Engineer in your terminal (0.1.17)

### Faster answers
- **Streaming:** answers appear as they are written, on every engine: Foundry Local, Ollama, OpenAI-compatible servers (LM Studio, llama.cpp, vLLM) and the Claude API. Settings → AI speed, agents & memory can turn it off.
- **Warm model:** the model loads while you type your first character, and stays loaded for the "keep warm" minutes after you last used the AI (10 by default; 0 unloads it after every answer). Nothing is sent to an internet provider to warm it.
- **Reused connections and prompt:** the connection to the engine stays open between questions. The fixed part of the prompt (instructions and tools) is the same every time, so local engines reuse what they already processed.
- **Timings:** the AI Engineer's STEPS list and the operator's status line show the time to the first text and the total time.

### Agents
Both the AI operator and the AI Engineer work as agents:
- They plan, call tools, look at the results and continue until they can answer, up to the **step limit** (12 by default).
- Independent read-only lookups run at the same time.
- **■ Stop** cancels at any point. In the AI Engineer, Stop also sends Ctrl+C to a command it is running in your terminal.
- **STEPS** (AI Engineer) lists every plan, tool call and result with its time. The operator shows the same lines in the chat.
- **Agent** (a tick box next to the model, per conversation) turns tools off for plain answers.
- **Model per chat:** the model box next to the conversation (AI Engineer) or in the header (operator) picks another model of the same engine for this chat only. Settings keep the default.
- **Models without tool calling** are detected (Ollama reports it) or recognised when the server refuses tools. They get the tools described in the prompt instead, so smaller and older models can still act as agents. The step log notes when this happens.

### The AI Engineer commanding your terminal
Choose the session under **TARGET TERMINAL** as before. In agent mode the AI Engineer then works in that session itself:
- **Running commands:** each command is shown with its risk and reviewed by you (risky ones need typing, as in the table above).
- **Auto-run read-only commands in the target session:** a tick box under TARGET TERMINAL, **off by default**. When it is on, commands that only read (`df -h`, `journalctl …`, `systemctl status …`, `Get-Service`) run without a review. Never auto-run:
  - anything that changes, is sensitive or destructive;
  - `sudo`;
  - interactive programs (`top`, `less`, editors);
  - commands that don't end on their own (`tail -f`, `journalctl -f`, `ping` without `-c`, `watch`);
  - any command in a **PRODUCTION** session.
- **Reading the screen:** the AI can read what the session shows (masked, and marked as untrusted data). It asks first unless auto-run is on.
- **Sending keys:** answers to prompts, pagers and TUIs (`q`, `yes{ENTER}`, `{CTRL+C}`, `{UP}`). Always reviewed; a line ending in Enter is judged like a command.
- **Ctrl+C:** stops the AI's own command at once; anything else asks.
- **Another session:** the AI can only *ask* to switch the target, or to open a new SSH session to a saved host. Your yes is the choice.
- **Audit:** everything is audited: auto-runs, screen reads, keys, Ctrl+C and target changes.

### More tools
New tools:
- **Infrastructure:** the actions possible on an object right now, including snapshots, clone, migrate and backup, with their inputs.
- **Cloud screens:** any action from a cloud provider's screen (attach a volume, enable backups, set reverse DNS…). You approve the exact API request. Deletes, consoles and anything that needs a typed name or a password stay on the screen.
- **Notes and incidents:** add to a note (its history is kept), open an incident, add an entry to an incident's timeline.
- **Transfers:** the transfer queue and recent history.
- **Portal browser:** list bookmarks and open one for you. The AI never sees pages, cookies or sign-ins.
- **Shared library add-on:** the libraries and their shared hosts, never credentials.

Every change asks first and is audited.

### The memory guard
On 19 October the app froze when a 20B model at a 64K context and Foundry Local together pushed the GPU's memory into system RAM. The guard prevents that:
- **High pressure** (commit charge ≥ 85 %, or the Ollama model more than 1 GB outside GPU memory): a smaller context (8K) and the model is unloaded right after the answer.
- **Critical pressure** (≥ 93 %): a 4K context.
- **Foundry Local:** its models are unloaded when memory is tight and it isn't the engine you use, or when it is but you haven't used the AI for the keep-warm time. Foundry Local keeps running and loads the model again on the next question.
- It never stops Ollama or Foundry and never unloads another program's Ollama model.
- **Settings → AI speed, agents & memory** shows the current reading and the guard's last action.

## AI tools across the app (0.1.11)
The AI operator also has tools that features register (the capability registry, `Services/Capabilities.cs`; add-ons reach the same list):
- **Context:** the current context (names only).
- **Infrastructure:** inventory and actions (same checks and approvals as the Infrastructure screen).
- **Cloud:** any cloud provider's resource lists.
- **Terminals:** the terminal sessions, and running a command in the chosen one (same review).
- **Notes and incidents:** search and read them (off by default; each read asks).
- **Documents:** PDF text.
- **Runbooks:** create a note (you see the full text and approve it).

Everything read from servers, APIs, terminals, notes or documents reaches the model fenced as untrusted data. Both AI prompts tell the model that such text is never an instruction. Answers cite `[note <id>]`, `[incident <id>]` or the file path.
