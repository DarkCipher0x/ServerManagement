# DarkCipher ServerManagement 0.1.15 (2026-10-19)

## New features

### Portal browser add-on: web UIs in tabs
Install `com.darkcipher.portal-browser-1.0.0.dcxaddon` (Add-ons → ＋ Install add-on…). It contains no program; it switches on a browser built into the app for router, switch, NAS, Proxmox / Unraid, out-of-band and provider web UIs.

- **Portals** in the sidebar (SERVERS): saved portals with folders, a filter, and Open / Open in a new window / Edit / Delete.
- **Host web UIs:** right-click a host → 🌐 Open web UI → its saved web UIs, or ＋ Add web UI… (pre-filled with `https://<host>/`).
- **Tabs or windows:** portals open as tabs in the main window, or as separate windows (Portals → Open portals in). Any portal tab pops out and docks back like a terminal.
- **A browser profile per environment:** PRODUCTION, TEST, LAB, DEVELOPMENT, LOCAL and general each have their own cookies, so production sign-ins never mix with the lab. Named profiles ("home lab") for anything that needs its own cookie jar. The tab shows the environment label and the profile.
- **Clear address bar:** a security chip (🔒 trusted HTTPS, 🔒 pinned, ⚠ Not secure, ⛔ Untrusted certificate, ⛔ CERTIFICATE CHANGED), and token-like query values (token, ticket, vncticket, password…) shown as "…".
- **Self-signed certificates are pinned, never ignored:** an untrusted certificate is refused with its SHA-256; after you compare it, **Trust this certificate…** pins it for that host:port only. A different untrusted certificate there later is refused as CERTIFICATE CHANGED. Pins are listed on the Portals screen (Forget).
- **Downloads ask first** (name, size, type, folder; a warning for files that can run code) and go to the folder you chose; nothing is overwritten.
- **Pop-ups stay in the app** as tabs in the same profile, and close when the page closes them.
- **No saved passwords:** the browser's password manager and form autofill are off. **⚿ Fill sign-in** fills the page from a vault password set on the portal (or its host), only on the portal's own address, and warns on plain HTTP.

### Shared library add-on: team hosts and credentials
Share hosts and credentials with your team through a folder or file share (SMB, a NAS folder, or a synced OneDrive / Syncthing folder). Sidebar → VAULT → **⇄ Shared library**.

- **End-to-end encrypted per member.** Each person has their own key pair, made on their PC. Every host or credential is encrypted under a collection key that is wrapped for each member allowed to read it, and every change is signed. The folder only ever holds ciphertext, signatures and public keys: no names, addresses, users or secrets.
- **Create, hand out, approve.** Create a library… makes you its owner and saves the team add-on (it contains no secret). Colleagues install it, Join, and read you their fingerprint; you approve them with that fingerprint and choose their role (member or admin) and, per collection, editor or reader.
- **Collections** keep a 10–50 person team manageable: Core infra, Customer X, Network… Only people granted a collection can read it.
- **Beside your own items, never over them.** Shared hosts appear in Hosts under "Shared · <library>" and under All hosts; shared credentials appear in Credentials and in every credential picker. Both are marked ⇄. Sync never changes your own hosts or credentials. **Copy to my hosts / vault** makes your own copy; **Publish to a shared library** copies one of yours into a collection after showing exactly what goes. Your own hosts can use a shared credential, so a rotated team password reaches them.
- **Conflicts are never silent.** Two people saving the same item at once get a CONFLICT with both versions kept; an editor picks one.
- **Works offline.** The last good copy is cached (encrypted) on each PC and used when the share can't be reached or Offline mode blocks it; edits wait and are sent on the next sync.
- **Removing someone re-keys.** Every collection they could read gets a new key and is re-encrypted, their PC drops its copy on the next sync, and a **rotation checklist** lists every credential they could see, to change on its targets.
- **Audit.** Admins see a signed, hash-chained shared audit from every member (Shared audit…). Using a shared credential, copying one and handing one to an add-on are also in your own Audit log.
- **Tamper and roll-back detection.** Files changed, forged by a reader, rolled back to older versions or deleted without a signed delete are rejected or flagged, and the newer cached copy is kept.
- **Add-on SDK:** new permission `library.read` (shared hosts in `hosts.list`, flagged `shared`, never secrets); `credentials.request` can offer shared credentials, labelled.

## Privacy
- No telemetry, and SmartScreen look-ups are off in the portal browser. Offline mode applies to every page and request.
- Privacy & network lists the portal browser and your saved portals by network class.
- Cookies and site storage are kept by the WebView2 runtime under the app's local data folder, protected by Windows (DPAPI), not by the app's own encrypted store. Bookmarks and certificate pins are in the encrypted store.

## Behaviour changes
- The Vultr portal / console windows share the portal browser's offline-mode guard (no change in behaviour).

## Known limitations
- Shared library: anyone with write access to the share can delete or roll back files. This is detected and flagged, not prevented. Reads are audited by each member's own app. Ownership can't be handed to another admin yet. Tested with simulated members on one PC, not yet on a real share with several PCs.
- A certificate that Windows trusts is accepted even if you pinned a different one for that host:port.
- HTTP Basic / Windows (NTLM) sign-in uses the browser's own prompt and isn't filled from the vault.
- Portal tabs are not reopened after a restart or a crash.
